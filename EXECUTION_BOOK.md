## Decision Log

| ID | Decision | Why | Alternative Rejected |
|----|----------|-----|------------------------|
| D1 | Node/TypeScript full stack (Next.js + Node services + Postgres/Redis, pnpm/Turborepo monorepo) | Principal's choice for consistency across a broker-adapter, AI-agent, and dashboard-heavy system; one language across the stack | Python backend + TS frontend (better for ML-heavy quant work, but adds a second toolchain/language boundary) |
| D2 | One sprint per Part — 10 sprints total | Principal's choice; matches the existing 10-Part plan directly | Splitting into 3–5 sprints per Part (~30–40 total) for smaller per-session scope |
| D3 | Roles modeled as an enum (`'admin'\|'trader'\|'viewer'`) on `users.role`, not a separate `roles`/`user_roles` table | Sprint 2 scope only needs a fixed, small role set for RBAC gating; keeps schema and migration simple | Normalized roles table with join table (defers well to future many-role/many-permission needs, but is unneeded complexity for the current 3-role skeleton) |
| D4 | `packages/event-bus` added as a new shared package (not in the original folder tree) wrapping ioredis pub/sub | Task 2.5 needs a reusable, testable pub/sub abstraction that any future service (market data, CIO engine, etc.) can import, rather than each service hand-rolling its own ioredis wiring | Inline ioredis usage directly in `services/auth` (would work for Sprint 2 alone but forces duplicate pub/sub boilerplate into every later service) |
| D5 | Sprint 3 built against a broker-agnostic `BrokerClient` port with a `SimulatedBrokerClient` test double, real `SmcGlobalBrokerClient` parked | SMC Global's API is not yet public and no credentials exist to build/test against (Principal confirmed "SMC Global broker's API is still coming soon"). Blocking all of Sprint 3 on an external dependency with no ETA would stall Market Data, and everything downstream (Research Engine, AI Council, Trading) that depends on it. A port + simulated implementation lets 3.3–3.6 (ingestion, normalization, streaming, historical import, fail-loud outage handling) be built and genuinely tested today, with the real adapter swapped in later behind the same interface, zero downstream rework | Waiting on SMC Global before starting any of Sprint 3 (keeps the plan "pure" but stalls 6+ sprints' worth of dependent work for an external dependency with no committed date) |
| D6 | Sprint 4's five analysis modules (task 4.1's technical indicator library and 4.2–4.5) were built as real, executable code inside `services/research` instead of `knowledge/indicators` as SPRINT_BOOK.md task 4.1 literally names it | `knowledge/*` (`indicators`, `options`, `strategies`, `prompts`, `glossary`, `courses`, `market-structure`) are all `.gitkeep`-only placeholders and are **not** registered in `pnpm-workspace.yaml` (which only lists `apps/*`, `services/*`, `services/broker/*`, `packages/*`) — there is no way to build, lint, or test TypeScript living there. `services/research` is already a properly-scaffolded workspace package per the repo's own folder tree, so it is the correct home for real, tested code; `knowledge/*` is reserved for future human-readable reference content only (glossary entries, course material, etc.), never executable modules | Creating `knowledge/*` as new pnpm workspace packages (would work, but silently diverges from the folder tree's own stated intent — `knowledge/` reads everywhere else in the repo as documentation/reference, not code — and would need its own new workspace-glob entry with no precedent) |
| D7 | `IndicesAgent`'s `TInput` is `TechnicalAnalysisResult` — the exact contract `TechnicalAgent` consumes — and it delegates directly to an internal `TechnicalAgent` instance, only relabeling the `expert` field to `'indices'`, instead of a dedicated `analyzeIndices()` Research Engine module | Sprint 4 never built a dedicated indices analysis module; `analyzeTechnical()` is already symbol-agnostic and works unchanged on any OHLCV series, including an index like NIFTY 50 or SENSEX. Inventing a parallel Research Engine module and a new shared-types result shape would duplicate the exact same RSI/EMA/MACD/breakout interpretation logic already proven in 4.1, for no behavioral difference | Building a standalone `analyzeIndices()` in `services/research` plus a new `IndicesAnalysisResult` type (would work, but is pure duplication — an index's OHLCV series has no structural difference from a stock's that `analyzeTechnical()` doesn't already handle) |
